# Preference Update

Preference Agent 수정 전과 작업 전반에 아래 9개 원칙을 적용한다. 사용자가 명시적으로 변경을 요청하지 않은 동작과 계약은 보존한다. 이 원칙은 요청한 수정의 유지보수 기준이며, 전체 구조 개편이나 별도 정리 작업을 허가하지 않는다.

## 1. 요청 범위와 기존 동작 보존

요청과 관련된 내용만 수정한다. 언급하지 않은 기능·규칙·검증·예외 처리·복구는 보존하고, 재배치가 필요하면 가장 가까운 역할로 옮긴다. 추가 삭제가 필요하면 대상과 이유를 설명하고 확인받은 뒤 삭제한다. Search/Relation/Ranking/Stylist agent 파일을 임의로 추가·삭제하지 않는다. 진행 중인 평가와 기존 산출물을 변경하거나 덮어쓰지 않는다.

## 2. 현재 구조와 역할별 배치

먼저 `preference/contracts.py`와 실제 호출부에서 대상 버전·Runner·입출력·프롬프트를 확인하고 역할별로 코드를 배치한다. 지원 버전과 서비스·평가 실행기의 선택 버전은 구분하며, 최신 지원 버전을 기본값으로 자동 적용하지 않는다.

소스 루트: `src/fashion_recommendation_v2`

- 에이전트 실행·처리 조정: `agents/`
- 프롬프트: `prompts/`
- 입출력·저장 스키마: `schemas/`
- HTTP·서비스·백그라운드 처리: `server/`
- DB·이벤트 저장·재생: `storage/`
- Preference 전용 계약·정책·중립 계산: `preference/`

위 구조는 기존 파일 전체를 이동하라는 뜻이 아니다. 요청상 재배치가 필요한 파일만 옮기고 호출부·import를 함께 맞춘다. 역할별 버전 파일을 신설하면 프롬프트와 스키마의 이름을 맞춘다.

```text
prompts/preference/<role>/preference_<role>_vN.py
schemas/preference/<role>/preference_<role>_vN.py
```

v0의 특징 추출·수치 집계, v1~v4의 취향 해석·프로필 저장, 후속 Ranking의 후보 선호 점수 계산을 구분한다. 코드로 처리하는 업무에 불필요한 프롬프트를 만들지 않는다. 공용 도우미는 중립 코드에 두고 불필요한 빈 파일은 만들지 않는다.

## 3. 규칙의 단일 기준 위치

규칙별 기준 위치를 하나로 유지한다.

- 필드명·자료형·필수 여부·허용값: 스키마
- 상품 특징별 허용 근거·인용 경로: 코드 출처 정의
- v0 특징 정규화·동의어·카테고리 해석, v1~v4 취향 해석·scope·importance·confidence: 해당 버전과 역할의 공통 의미 규칙
- v0 수치 행동 가중치·시간 감쇠·집계, 각 실행 경로의 예산·최종 적용·제외: 코드 정책
- 단계별 업무: 공통 규칙에 추가하는 단계 전용 지시

출처 안내와 코드 검증은 같은 정의를 사용한다. 버전별 역할을 보존한다.

- v0: LLM이 상품 특징을 추출하고, 코드는 행동 가중치·수치 집계·시간 감쇠를 계산한다. 구버전 재현을 위해 이 경로를 유지한다.
- v1~v4: 코드는 유효 이벤트 재생·동일성 검증·근거와 입력용 행동 요약을 준비하고, LLM은 상품 근거와 행동을 바탕으로 `interpretations + summary`를 생성한다. 코드는 스키마·근거·카테고리 참조를 검증하고 관리 필드·해석 ID를 부여해 저장한다. 별도 특징 추출 LLM, 정규화 features/title_keywords, 수치 선호 집계·시간 감쇠·코드 summary를 도입하지 않는다.
- v4의 `confidence`는 취향 추론의 확실성, `importance`는 개인화에서 고려할 우선순위다. 서로 독립적인 정성 등급이며 확률이나 최종 Ranking 가중치로 바꾸지 않는다.

생성·검증·교정이 동일한 대상 계약을 사용하게 한다. 감사가 있다면 감사 판정 스키마와 대상 응답 스키마를 구분한다. 요청 없이 새로운 감사 호출이나 정책을 추가하지 않는다.

## 4. 입력 경로와 근거 출처

입력 경로와 근거 출처를 보존한다.

공통 서비스 입력은 `저장된 ItemSnapshot → InteractionEvent → UpdateInput → PreferenceAgent`이며, 이후 대상 계약에 따라 분기한다.

- v0: `PreferenceRunner`를 사용한다. 특징 추출 입력은 `ItemSnapshot → Observation → AnalysisUnit → PreferenceBatchInput`이다.
- v1~v4: `PreferenceInterpretationRunner`가 `preference/interpretation_input.py:prepare_input`으로 유효 이벤트·상품·카테고리·출처별 근거·as_of·기존 해석 프로필 문맥을 준비한다. 대상 버전의 `InterpretationInput → InterpretationOutput → 저장 프로필` 계약을 사용한다. v0 수치 특징 통계를 해석 입력으로 대체 주입하지 않는다.

`search_analysis`가 있는 상품은 기존 출처 선택 규칙에 따라 `item.title`·`item.category_path`와 Search 상품 근거를 사용한다. 제외된 mapper 속성이나 `raw_metadata`를 우회해서 다시 사용하지 않는다. Search 원응답·관찰·출처 간 비교 상태를 임의로 덮어쓰지 않는다. v0의 `preference/observations.py` 투영과 v1~v4의 `preference/interpretation_sources.py`를 구분한다. 해석 경로에서는 metadata·image_observation·metadata_image_consistency를 출처별 원값·타입으로 보존하고, 충돌을 병합하거나 v0 특징 투영으로 대체하지 않는다. Search 분석이 없는 구형 입력의 허용 목록은 유지하되, 출처 분리 attributes가 없는 구형 Search 분석을 해석 경로에 임의로 허용하지 않는다. 구형 입력 호환 경로는 명시적인 요청 없이 삭제하거나 확대하지 않는다.

상품·이미지·snapshot·이벤트·사용자 간 동일성 검증을 보존한다. 이미지 근거가 필요하다는 이유로 새 이미지 호출을 추가하지 않는다. 소재 조성을 이미지 질감으로 추정하지 않는다. Q·V·요청 충족 판정·순위를 사용자 선호 특징으로 학습하지 않는다. 상품 반응을 특정 속성에 대한 명시적 선호 발언으로 바꾸지 않는다.

## 5. 이벤트와 프로필의 의미

`record`/`cancel`/`correct`, 대상 이벤트 연결, 중복 방지, 수신 순서·처리 cursor·기준 시각을 유지한다. v0의 수치 시간 감쇠, 전체/카테고리 선호 적용·대체, 특징과 제목 키워드 중복 계산 방지는 v0에 보존한다. v1~v4에서는 as_of와 행동 시각을 LLM이 해석하고, 저장된 해석은 조회 시 수치 감쇠하지 않는다. global/category scope와 해당 참조 검증을 유지하며 v0의 수치 대체 규칙을 이식하지 않는다. 정보 부족·근거 충돌·중립·비선호·프로필 없음·처리 실패를 구분한다.

v0의 기존 특징 추출 캐시는 해당 입력·추출 버전과 맞을 때만 재사용한다. v1~v4는 계약과 manifest의 `cache_reuse=False`/`cache_used=False`를 유지하며, v0 특징 캐시를 읽어 해석을 대체하거나 덮어쓰지 않는다. 규칙 변경 시 대상 버전의 캐시 호환성·재추출 또는 재해석 필요 여부를 명시한다. 실패를 정상 빈 프로필이나 점수 0으로 바꿔 숨기지 않는다. 재시도·작업 잠금·버전 충돌·만료·삭제 후 저장 방지 등 기존 저장 및 복구 동작을 보존한다.

## 6. 원응답과 버전별 재현성

`model_response`의 필드명·값·타입·중첩 구조를 유지하고, `code_validation`과 정규화·집계 등 코드 파생 결과는 별도로 저장한다. 최초 응답과 교정 응답을 구분하고, 오류를 숨기려고 원응답의 필드를 삭제하거나 옮기지 않는다.

Preference 역할·버전 연결은 기존 `preference/contracts.py`를 기준으로 확인·수정하고 중복 정의하지 않는다. v0와 v1~v4의 분기, 저장 프로필 버전 및 하위 버전으로 덮어쓰기 방지를 보존한다. Search 버전 연결은 기존 `search/contracts.py`를 따르게 한다. 구버전 재현과 기존 결과를 보존하고, 과거 프롬프트의 연쇄 문자열 치환으로 새 규칙을 만들지 않는다. `schemas → prompts/agents`, `prompts → agents` 역참조와 순환 의존성을 만들지 않는다. 모델·호출 수·예산은 요청 범위에서만 변경한다.

## 7. 프로필 생성과 후속 사용

프로필 생성과 후속 사용을 구분한다. Orchestrator의 적용 대상 선택, Stylist의 해석, Ranking의 P 계산, Summary의 설명 입력을 확인하고, 변경된 계약을 실제로 소비하는 경로만 함께 맞춘다. 현재 요청 조건 우선 적용과 속성별 선호 제외 규칙을 보존한다. Search에 프로필 활용을 임의로 새로 연결하지 않는다.

스키마에 필드가 있다는 것과 실행 경로에서 전달·사용된다는 것을 구분해서 확인한다. 버전별 연결 누락은 별도로 보고하고, 보류한 수정은 다른 요청에 포함해 자동 적용하지 않는다.

## 8. 평가 입력과 결과 분리

Preference 평가 입력과 결과를 분리한다.

- 버전 기록: 저장소 루트 기준 `evals/preference/preference_eval_version.md`
- 결과 루트: `eval_results`

## 9. 수정 범위에 맞는 검증과 보고

규칙을 수정하면 스키마·프롬프트·출처 선택·코드 검증·교정·캐시·저장·후속 소비자가 모두 일치하는지 확인한다. 의존 관계 검사와 관련 회귀 테스트를 실행하고, 정상·실패·교정·재실패 및 이벤트 취소·정정 경로를 확인한다. 기존 기대값을 덮어써 테스트를 통과시키지 않는다.

코드 계산의 정확성과 상품 특징·개인화의 의미적 품질을 구분한다. 테스트 통과를 실제 선호 추론이나 추천 품질 향상으로 단정하지 않는다. 변경 위치·검증 결과·남은 제한을 보고하고, 실제 API 실행·모의 테스트·저장 결과 재생을 명확히 구분한다. 문서만 수정했다면 런타임 검증을 수행한 것처럼 보고하지 않는다. 실행하지 못한 검사는 이유와 미검증 범위를 밝히며 통과한 것으로 보고하지 않는다. 실제 API 실행은 사용자가 허용한 범위와 예산 안에서 수행한다.
