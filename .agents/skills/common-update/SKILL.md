# Common Update

여러 에이전트를 수정할 때 편집 전과 작업 전반에 아래 7개 공통 원칙을 적용한다. 이 원칙은 요청한 수정의 유지보수 기준이며, 전체 구조 개편이나 별도 정리 작업을 허가하지 않는다. 해당 에이전트의 개별 유지보수 스킬도 적용되는 경우, 그 스킬의 구체적인 계약·출처·정책 보존 규칙을 함께 따른다. 이 스킬을 적용하기 위해 기존 개별 스킬을 수정하거나 공통 규칙으로 대체하지 않는다.

## 1. 요청 범위와 기존 동작 보존

요청과 관련된 내용만 수정한다. 언급하지 않은 기능·규칙·검증·예외 처리·복구는 보존하고, 재배치가 필요하면 가장 가까운 책임을 가진 위치로 옮긴다. 요청 범위를 벗어난 추가 삭제가 필요하면 대상과 이유를 설명하고 확인받은 뒤 삭제한다. 에이전트 파일을 임의로 추가·삭제하지 않는다.

## 2. 역할과 파일 구조

기존 파일 구조를 존중하고, 같은 입출력과 의미 규칙을 공유하는 업무는 함께 관리한다. 역할이나 버전 전용 프롬프트·스키마가 필요하면 양쪽의 역할명과 버전이 대응되도록 이름을 맞춘다. 변경되지 않은 공통 계약을 역할·버전마다 복제하지 않는다. 공용 정책·출처 정의·도우미는 prompts/agents에 의존하지 않는 중립 코드에 두고, 불필요한 폴더나 빈 파일을 만들지 않는다.

## 3. 규칙별 기준 위치

규칙별 기준 위치를 하나로 유지한다.

- 필드명·자료형·필수 여부·허용값·값의 범위: 스키마
- 인용 가능한 경로·출처·참조 생성: 코드 출처 정의
- 기본값·우선순위·최종 적용·호출 예산·재시도: 코드 정책
- 해석·판단에 필요한 의미 규칙: 해당 역할의 공통 의미 규칙
- 생성·감사·교정 등 단계별 업무: 공통 규칙에 추가하는 전용 지시

출처 안내와 코드 검증은 같은 정의를 사용한다. 코드 정책 중 모델 판단에 필요한 내용은 LLM에도 전달하되, 최종 적용은 코드에서 처리한다. 생성·감사·교정은 동일한 평가 대상 계약을 사용한다. 감사 판정 스키마와 감사 대상 응답의 스키마는 구분한다. 이 원칙을 적용한다는 이유만으로 감사나 교정 호출을 새로 추가하지 않는다.

## 4. 원응답과 검증 결과 분리

검증 때문에 원응답을 재구성하지 않는다. `model_response`의 필드명·값·타입·중첩 구조를 보존하고, `code_validation`과 코드 파생 결과는 별도로 붙인다. 파싱·검증에 실패한 응답도 수신 원문과 실패 사유를 보존한다. 오류를 숨기려고 필드를 삭제·이동하거나 값을 채우지 않는다.

교정 응답은 최초 응답과 구분하고, 평가 대상·오류·교정 시도·최종 적용 결과를 연결한다. 기존 `null`·미평가·생략·실패의 의미와 fallback 정책을 보존한다.

## 5. 입력 계약과 출처 보존

입력 필드의 고정 경로·의미·출처를 유지한다. 사용자 원문·확장 또는 투영된 문장·다른 에이전트의 해석·관찰 사실·코드 파생 결과를 구분한다. 전달받은 구조화 값과 타입, 원문 인용, OR 관계를 보존한다.

원본과 투영본의 관계를 유지하고, 입력 투영에서 제외한 정보를 원본 보존용 필드로 다시 사용하지 않는다. 근거와 평가 대상의 연결을 유지하고, 다른 대상의 근거를 바꿔 인용하거나 없는 정보를 만들어 넣지 않는다. 다른 에이전트가 소유한 판단이나 정책을 요청 없이 재해석하지 않는다.

## 6. 역할·버전·의존 관계

기존 계약 또는 버전 선택 위치에서 입력·프롬프트·출력 스키마·입력 투영·코드 검증·교정·후속 소비자의 연결을 명확히 한다. 버전 선택 규칙을 여러 곳에 중복 정의하지 않는다. 서로 연결되는 에이전트의 버전은 구분해서 기록하고 호환성을 확인한다.

구버전 재현과 기존 결과·고정 입력·snapshot을 보존한다. 과거 프롬프트를 연쇄 문자열 치환해서 새 규칙을 만들지 않는다. `schemas → prompts/agents`, `prompts → agents` 역참조와 순환 의존성을 만들지 않는다. 공용 계약을 변경하면 다른 에이전트에 미치는 영향을 확인한다. 모델·배치 크기·병렬도·호출 수·예산·시간·출력 상한은 요청 범위에서만 변경한다.

검증 재사용을 다루는 변경에서는 `src/fashion_recommendation_v2/validation_reuse.py`의 공통 정의와 실제 적용 버전을 확인한다. 현재 적용 릴리스는 Orchestrator v5, Ranking v14, Summary v11이며, 지원되는 모든 버전에 자동 확대하지 않는다. Orchestrator 경로는 Ranking 인계 시점부터 재사용을 활성화한다.

- 성공한 순수 검증만 같은 요청 범위에서 재사용한다. 검증기는 입력을 변경하지 않고 첫 번째 인수를 그대로 반환해야 한다.
- 검증 대상과 비교 대상, 타입·필드·중첩·private/extra 상태, 검증기 식별 및 인자로 전달된 정책 범위가 동일한지 확인한다. 재사용 키를 상품 ID나 일부 필드로 축소하지 않는다.
- 실패 결과는 재사용하지 않는다. 스냅샷 생성이 지원되지 않거나 입력·정책이 달라지면 기존 검증을 다시 수행한다.
- 요청 종료 시 재사용 기록을 폐기하며 다른 요청·사용자로 넘기지 않는다. 원응답을 재구성하거나 동일성 확인 없이 검증을 건너뛰는 캐시로 바꾸지 않는다.

## 7. 일관성 검증과 결과 보고

규칙을 수정하면 스키마·프롬프트·입력 투영·코드 검증·교정·저장 결과·후속 소비자가 모두 일치하는지 확인한다. 의존 관계 검사와 관련 회귀 테스트를 실행하고, 변경과 관련된 정상·실패·교정 성공·교정 재실패·부분 처리 경로를 확인한다. 검증 재사용을 변경한 경우에는 동일 입력의 재사용뿐 아니라 입력/정책 변경 시 재검증, 실패 재실행, 요청 간 격리, 재사용 유무에 따른 결과·예외 일치도 확인한다. 기존 기대값을 덮어써 테스트를 통과시키지 않는다.

비교 평가에서는 변경 대상 외 입력·모델·예산·후속 설정을 고정하고, 차이가 있으면 명시한다. 고정 입력 교체나 데이터 재수집은 에이전트 변경과 구분한다. 변경 위치·검증 결과·남은 제한을 보고하고, 실제 API 실행과 모의/재생 테스트를 명확히 구분한다. 버전 업데이트를 요청한 경우 해당 에이전트의 기존 버전 기록 문서에 변경과 검증 내용을 기록한다.
