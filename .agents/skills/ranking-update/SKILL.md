# Ranking Update

Ranking Agent 수정 전과 작업 전반에 아래 8개 원칙을 적용한다. 사용자가 명시적으로 변경을 요청하지 않은 동작과 계약은 보존한다. 이 원칙은 요청한 수정의 유지보수 기준이며, 전체 구조 개편이나 별도 정리 작업을 허가하지 않는다.

편집 전에 요청 범위와 실제 실행 버전을 확인하고, 영향을 받는 입력 출처·계약·실행 경로·후속 소비자·검증 항목을 파악한다. 소스 경로는 체크아웃된 저장소의 `src/fashion_recommendation_v2/`를 기준으로 찾고, `evals/` 경로는 저장소 루트를 기준으로 찾는다.

## 1. 요청 범위와 기존 동작 보존

요청과 관련된 내용만 수정한다. 언급하지 않은 기능·점수·제외 기준·다양성·검증·예외 처리·복구는 보존하고, 재배치가 필요하면 가장 가까운 역할로 옮긴다. 요청 범위를 벗어난 추가 삭제가 필요하면 대상과 이유를 설명하고 확인받은 뒤 삭제한다.

기존 agent 파일인 `ranking.py`, `ranking_brain.py`, `ranking_runner.py`, `ranking_preferences.py`를 임의로 추가·삭제하지 않는다. Search·Relation 등 연관 agent 파일도 임의로 추가·삭제하지 않는다.

## 2. 파일 구성과 역할 경계

기존 파일 구성을 우선 유지하고 역할 경계를 명확히 한다.

- Brain/프롬프트: 해당 실행 경로에서 필요한 LLM 판단
- Runner: 입력 검증, 실행 순서, 점수 계산과 추천 선정
- Preference: 취향 적용 범위와 선호 점수
- 스키마: 입력·출력 계약과 구조적 불변 조건
- 공용 코드: 근거 검증, 판정 파생, 점수 정책 등 공유 규칙

폴더 구분을 늘리는 것 자체를 목적으로 재구성하지 않는다. 프롬프트와 스키마를 버전별로 분리할 필요가 있으면 역할명·버전명을 대응시키고, 실제 연결 관계를 명시한다. 코드 전용 스키마에는 대응 프롬프트나 빈 파일을 억지로 만들지 않는다.

## 3. 규칙의 단일 기준 위치

규칙별 기준 위치를 하나로 유지한다.

- 필드명·자료형·필수 여부·허용값: 스키마
- 인용 가능한 필드 경로·근거 출처: 공용 출처 정의
- hard/soft·OR·범위·충족과 확인 가능성의 구분: 공통 의미 규칙
- 상태별 점수·가중치·임계값·제외·다양성·동점 처리: 코드 정책
- 단계별 LLM 업무: 공통 규칙에 추가하는 단계 전용 지시

생성 코드와 출력 검증기가 같은 점수·정책 정의를 사용하게 한다. LLM에 코드의 최종 점수·순위 결정을 중복으로 맡기지 않는다. 생성·감사·교정은 동일한 대상 계약을 사용하고, 감사 판정 스키마와 감사 대상 응답의 스키마는 구분한다.

## 4. 원응답과 코드 파생 결과 분리

`model_response`의 필드명·값·타입·중첩 구조와 Search의 저장 판정을 보존하고, `code_validation`·`derived_judgment`·점수 내역·복구 진단은 별도로 기록한다.

검증을 통과시키려고 원응답의 필드를 삭제하거나 옮기지 않는다. 근거 부족이나 충돌 때문에 코드가 판정을 보정하면 원판정·파생 판정·적용 규칙·보정 이유를 추적할 수 있게 한다. 관찰 누락/검증 실패와 모델의 `unknown` 판정을 구분하고, 코드 대체값을 실제 모델 관찰처럼 저장하지 않는다.

## 5. 입력 출처와 버전별 우선순위

다음 입력 출처와 버전별 우선순위를 유지한다.

- `item.raw_metadata`: 판매자 원본 정보
- `evaluation_item`: Search 평가 당시 상품 스냅샷
- `search_analysis`: Search의 판정·관찰·근거·충돌·감사 기록
- `item`의 최종 속성: Mapper가 정리한 상품 정보
- `resolved_requirements`: 해당 입력의 확정 요구사항
- `candidate.sources`/`search_attempts`: 검색 출처와 검색 신호
- 구형 입력의 `preference_profile`: 해당 버전 계약으로 직접 전달된 취향 정보
- v11~v14의 취향 입력: 공개 입력의 `personalization_mode`와 Runner의 `profile_lookup`으로 조회·고정한 프로필 bundle
- Relation 출력: 해당 요청·앵커·후보에 대한 관계 평가

v11~v14의 공개 입력에 구형 `preference_profile` 필드를 추가하지 않는다. Warm에서는 인증된 서비스 또는 고정 파일의 `profile_lookup`을 사용하고, `freeze_bundle`로 고정한 프로필·카테고리·근거 인덱스를 후보 판단과 재검증에 동일하게 사용한다. Cold의 미조회, 정상 empty/not_found, 조회 실패를 구분하며 실패를 프로필 없음으로 숨기지 않는다.

R·V·Q·T·P·Relation·다양성이 어떤 입력을 사용하는지 명시한다. 요청 없이 Mapper 속성으로 Search 판정을 대체하거나 그 반대로 바꾸지 않는다. 평가 스냅샷의 근거를 최종 `item`의 근거로 잘못 검증하지 않는다. 상품 ID·이미지·요구사항·관찰 버전과 기존 해시 검증을 유지한다.

사용자 원문, Stylist 해석, `attribute`/`value`/`source_text`와 OR 값·타입을 보존한다. 제외된 조건이나 검색용 확장 조건을 점수 조건으로 되살리지 않는다. Cold에는 취향을 임의로 적용하지 않는다. 사람 GT는 채점 전용으로 유지해 Ranking 입력·프롬프트에 넣지 않는다.

## 6. Ranking과 상위 단계의 책임

Search의 이미지 분석·후보 통과 판단과 Ranking의 점수·추천 제외를 구분한다. 요청 없이 Ranking에 이미지 재분석이나 추가 LLM 호출을 도입하지 않는다. 저장 분석 재사용 경로와 기존 LLM 실행 경로를 구분하고, 실제 실행되지 않는 프롬프트만 수정한 뒤 동작이 바뀌었다고 보고하지 않는다. 추가 호출 금지는 v11~v14에 이미 존재하는 프로필 조회 요청·후보별 취향 적합성 판단/교정 호출을 제거하라는 뜻이 아니다. LLM의 취향 판단과 코드의 P 매핑·최종 점수·선정을 구분하고, 점수 재생·출력 검증은 기존대로 추가 LLM 호출 없이 수행한다.

R의 조건 충족도, V의 시각적 확인 가능성, Q의 사진 상태를 혼동하지 않는다. 현재 버전의 `restricted` 제외, 최소 적합도, 관찰 누락 처리와 Relation·Preference 결합 정책을 보존한다. 후속 점수나 추천 개수 보충으로 제외 정책을 우회하지 않는다.

v12~v14의 두 단계 선정을 보존한다. 숫자 P가 있는 적격 후보를 먼저 선정하고(`P=0`도 활성), 부족분은 정상적인 P 미적용/판단 불가 후보를 baseline 점수 체계로 보충한다. `P=0.5`의 neutral, 정상 `P=null`, 호출·검증 실패/예산 미평가를 구분한다. 실패·미평가 후보를 보충으로 되살리지 않고, 서로 다른 점수 체계의 두 그룹을 Total로 합쳐 재정렬하지 않는다. 원래 후보 풀의 score views와 그룹 연결 후 selection 순위를 구분한다.

v13/v14의 similarity 요청은 입력이 Warm이어도 해당 요청에서만 Cold로 처리한다. `personalization_policy.py`의 공통 정책을 따르고 사용자·세션 상태나 다른 요청의 모드를 변경하지 않는다. 구버전에 이 정책을 소급 적용하지 않는다.

## 7. 역할·버전 연결

먼저 서비스·평가 스크립트·Runner 기본값이 실제 사용하는 버전과 지원 가능한 버전을 구분해서 확인한다.

Ranking 정책, 입력 Search 계약, 관찰 스키마, 점수 정책, 출력 스키마·검증기, 실제 사용하는 프롬프트의 연결을 명시한다. 기존 버전 연결 위치를 우선 활용하고, 중앙 계약 정의가 필요하면 `ranking_contracts.py` 같은 중립 모듈로 정리한다. Search 관찰 계약은 Search의 계약 정의를 참조하고 중복 정의하지 않는다.

구버전 재현과 기존 결과를 보존한다. 과거 프롬프트를 연쇄 문자열 치환해서 새 규칙을 만들지 않는다. `schemas → prompts/agents`, `prompts → agents` 역참조와 순환 의존성을 만들지 않는다. 모델·호출 수·예산·동시성·재시도 정책은 요청 범위에서만 변경한다.

## 8. 수정·검증·보고 연결

규칙을 수정하면 스키마·프롬프트·코드 계산·검증·교정·후속 소비자가 모두 일치하는지 확인한다. API·Summary·갤러리·평가 지표·엑셀도 변경의 영향을 받는 부분을 확인한다. 기본 점수, 다양성 적용 후 점수, 최종 선정 순위를 혼동하지 않는다.

의존 관계 검사와 관련 회귀 테스트를 실행하고, 정상·경계값·실패·교정·재실패·대체 처리 중 해당하는 경로를 확인한다. Cold/Warm, Relation 유무, 구버전 재생 등 영향을 받는 조합도 확인한다. 코드 재사용 경로에 불필요한 LLM 호출이 생기지 않았는지 검증한다.

기존 기대값을 단순히 덮어써 테스트를 통과시키지 않는다. 의도적으로 기대값이 바뀌면 변경된 규칙과 새 기대값의 근거를 설명한다. 고정 입력·GT·과거 결과를 덮어쓰지 않고, `evals/ranking/ranking_eval_version.md`의 해당 버전에 변경을 기록한다.

변경 위치·실제 적용 버전·검증 결과·남은 제한을 보고하고, 실제 API 실행, 모의/재생 테스트, 사람 GT 기반 품질 평가를 구분한다. 실행하지 못한 검사는 이유와 미검증 범위를 밝히며 통과한 것으로 보고하지 않는다. 실제 API 실행은 사용자가 허용한 범위와 예산 안에서 수행한다.
