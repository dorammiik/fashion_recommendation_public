# Relation Update

Relation Agent 수정 전과 작업 전반에 아래 7개 원칙을 적용한다. 사용자가 명시적으로 변경을 요청하지 않은 동작과 계약은 보존한다. 이 원칙은 요청한 수정의 유지보수 기준이며, 전체 구조 개편이나 별도 정리 작업을 허가하지 않는다.

편집 전에 요청 범위와 영향을 받는 실행 버전을 확인하고, 입력 출처·계약·근거 투영·검증·교정·후속 소비자의 연결을 파악한다. 소스 경로는 체크아웃된 저장소의 `src/fashion_recommendation_v2/`를 기준으로 찾고, `evals/` 경로는 저장소 루트를 기준으로 찾는다.

## 1. 요청 범위와 기존 동작 보존

요청과 관련된 내용만 수정한다. 언급하지 않은 기능·규칙·검증·예외 처리·교정·복구는 보존하고, 재배치가 필요하면 가장 가까운 역할로 옮긴다. 추가 삭제가 필요하면 대상과 이유를 설명하고 확인받은 뒤 삭제한다. Relation/Search agent 파일을 임의로 추가·삭제하지 않는다. Relation 수정 때문에 Search의 후보 선정이나 Ranking의 점수·가중치를 요청 없이 변경하지 않는다.

## 2. 기존 구조와 역할 경계

Relation의 기존 파일 구조를 유지하고, 같은 입출력과 의미 규칙을 공유하는 업무를 함께 관리한다. 버전 전용 프롬프트·스키마가 필요하면 이름과 버전을 대응시킨다.

```text
prompts/relation_vN.py
schemas/relation_vN.py
```

기존 공통 스키마는 유지하고, 변경되지 않은 계약을 버전마다 복제하지 않는다. 관계 의도·근거 투영·관계 평가·감사·교정의 책임을 구분하되, 이를 위해 불필요한 폴더나 빈 파일을 만들지 않는다. 공용 정책·출처 정의·도우미는 prompts/agents에 의존하지 않는 중립 코드에 두고, 공용 계약 변경의 영향 범위를 확인한다.

## 3. 규칙의 단일 기준 위치

규칙별 기준 위치를 하나로 유지한다.

- 필드명·자료형·필수 여부·허용값·점수 범위: 스키마
- 인용 가능한 근거 경로·출처·참조 생성: 코드 출처 정의
- 점수 적용·미평가 처리·호출 예산·재시도: 코드 정책
- compatibility/similarity, 근거 충분성·충돌·불확실성: Relation의 공통 의미 규칙
- 생성·감사·교정의 단계별 업무: 공통 규칙에 추가하는 전용 지시

출처 안내와 코드 검증은 같은 정의를 사용한다. 코드 정책 중 모델 판단에 필요한 내용은 LLM에도 전달하되, 최종 적용은 코드에서 처리한다. 생성·감사·교정은 동일한 평가 대상 계약을 사용한다. 감사 판정 스키마와 감사 대상 응답의 스키마는 구분한다. 이 원칙을 적용한다는 이유만으로 감사나 교정 호출을 새로 추가하지 않는다.

## 4. 원응답과 코드 파생 결과 분리

검증 때문에 원응답을 재구성하지 않는다. `model_response`의 필드명·값·타입·중첩 구조를 보존하고, `code_validation`과 코드 파생 결과는 별도로 붙인다. 파싱·검증에 실패한 응답도 수신 원문과 실패 사유를 보존한다. 오류를 숨기려고 필드를 삭제·이동하거나 값을 채우지 않는다.

교정 응답은 최초 응답과 구분하고, 대상 상품·오류·교정 시도·최종 적용 결과를 연결한다. 기존 `null` 점수, 미평가, 생략, 실패의 의미를 서로 바꾸지 않는다. Relation 평가 실패를 후보 삭제나 임의의 0점 처리로 바꾸지 않고, 기존의 유효 평가 보존 및 후속 fallback 정책을 유지한다.

## 5. 고정 입력 경로와 출처

Relation 입력의 고정 경로와 출처를 유지한다.

- `intent`: 해결된 관계 유형·근거 문구·앵커 참조
- `anchor_item`: 실제로 선택된 기준 상품의 원본 스냅샷
- `anchor_search_analysis`: 그 기준 상품에 대응하는 Search 평가
- `candidate_set`: 평가 대상 후보 집합의 원본
- `candidate_set.candidates[].item`: 해당 후보 상품
- `candidate_set.candidates[].search_analysis`: 해당 후보의 Search 평가

특정 상품 앵커와 일반 카테고리 앵커를 구분하고, 상품 ID·이전 추천 순위·앵커 스냅샷의 연결을 임의로 바꾸지 않는다. 일반 카테고리 앵커에 없는 색상·소재·핏 등을 만들어 넣지 않는다. similarity와 compatibility의 기존 적용 조건을 유지한다.

상품·이미지·평가 근거의 동일성과 재사용 유효성 검증을 유지하고, anchor 근거와 candidate 근거를 서로 바꿔 인용하지 않는다. Search의 관찰 사실과 조건 판정·품질 점수·Ranking 점수를 구분한다. 입력 투영에서 제외한 정보는 원본 보존 필드를 통해 다시 사용하지 않는다.

사용자 원문·검색용 문장·Stylist 해석을 준비 단계에서 사용하는 경우, 각각의 기존 출처와 `attribute`/`value`/`source_text`, OR 값·타입을 보존한다. Relation 입력에 없는 필드를 임의로 추가하거나, Search의 성별·hard/soft 정책을 Relation에서 새로 해석하지 않는다.

Search v52/v53의 스트리밍 연결을 수정할 때는 `relation/streaming_v52.py`와 Orchestrator 연결을 함께 확인한다. Search 검증을 통과한 확정 후보만 제출하고, 앵커·관계 의도·후보·Search 평가·evaluation_item·요구사항 스냅샷의 동일성으로 재사용을 판단한다. 상품 ID만 같다는 이유로 변경된 근거의 결과를 재사용하지 않는다.

Search 종료 후 최종 후보 풀과 근거 키를 다시 대조한다. 제거된 후보나 이전 근거의 결과는 Ranking에 전달하지 않는다. 변경된 근거는 남은 기존 예산 안에서 평가하고, 예산 소진을 임의 점수로 바꾸지 않는다. 이전 근거에 사용한 호출도 예산에 포함하고, 최초 평가 완료 후 기존 한도 내 실패 후보 교정·최종 Relation 검증을 마친 뒤 Ranking을 실행하는 순서를 보존한다. success/fail/unevaluated와 최종 풀 반영 여부·최초/교정 시도 기록, 실패 시 작업 풀 정리를 유지한다. 이 경로를 구버전이나 관계 없는 요청에 자동 적용하지 않는다.

## 6. 역할·버전 연결

Relation의 기존 버전 선택 위치에서 입력·프롬프트·출력 스키마·근거 투영·코드 검증·교정·후속 소비자의 연결을 명확히 한다. 버전 선택 규칙을 여러 곳에 중복 정의하지 않는다. 별도 계약 모듈이 필요하면 요청 범위에서 중립 코드로 분리하되, 기존 구조를 일괄 개편하지 않는다.

Relation 평가 버전, 입력 CandidateSet의 Search 버전, 후속 Ranking 버전은 구분해서 기록하고 호환성을 확인한다. 구버전 재현과 기존 결과·고정 입력·snapshot을 보존한다. 과거 프롬프트를 연쇄 문자열 치환해서 새 규칙을 만들지 않는다. `schemas → prompts/agents`, `prompts → agents` 역참조와 순환 의존성을 만들지 않는다. 모델·배치 크기·병렬도·호출 수·예산·시간 및 출력 상한은 요청 범위에서만 변경한다.

## 7. 수정·검증·보고 연결

규칙을 수정하면 스키마·프롬프트·근거 투영·코드 검증·교정·저장 결과·Ranking/Summary 등 후속 소비자가 모두 일치하는지 확인한다. 의존 관계 검사와 관련 회귀 테스트를 실행하고, 정상·실패·교정 성공·교정 재실패·부분 평가 경로를 확인한다. 특정 상품/카테고리 앵커, similarity/compatibility, 근거 누락·잘못된 참조·상품/이미지 불일치·충돌·불확실성 중 변경과 관련된 경로를 검증한다.

기존 기대값을 덮어써 테스트를 통과시키지 않는다. A/B 평가에서는 변경 대상 외 입력·후보·앵커·모델·예산·Ranking 설정을 고정하고, 차이가 있으면 명시한다. 고정 입력을 교체하거나 후보를 다시 수집하는 일은 Relation 평가 변경과 구분한다.

변경 위치·검증 결과·남은 제한을 보고하고, 실제 API 실행과 모의/재생 테스트를 명확히 구분한다. 버전 업데이트를 요청한 경우에는 `evals/relation/relation_eval_version.md`에 변경과 검증 내용을 기록한다. 실행하지 못한 검사는 이유와 미검증 범위를 밝히며 통과한 것으로 보고하지 않는다. 실제 API 실행은 사용자가 허용한 범위와 예산 안에서 수행한다.
